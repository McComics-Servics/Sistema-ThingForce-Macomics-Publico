## FASE 0.5 — DESCOMPOSICIÓN OBLIGATORIA DEL PROBLEMA (ANTES DE CUALQUIER SOLUCIÓN)

> **Esta fase es obligatoria para TODOS los niveles del semáforo. No se puede saltar.**

Antes de proponer cualquier solución, la IA debe descomponer el problema completamente siguiendo estos 10 pasos:

1. **Descomponer en componentes fundamentales** — identificar todas las piezas del problema, no solo las visibles
2. **Explicar cada parte e interacciones** — cómo se relacionan entre sí, qué depende de qué
3. **Describir el flujo completo inicio-fin** — desde el estado actual hasta el estado deseado, paso a paso
4. **Identificar puntos críticos de fallo** — dónde normalmente ocurren errores, cuellos de botella o pérdidas de datos
5. **Indicar variables que afectan rendimiento o estabilidad** — parámetros, condiciones, entornos, dependencias externas
6. **Proponer la arquitectura más eficiente y escalable desde el principio** — no la más rápida ni la más fácil
7. **Si falta información importante, DETENER y preguntar** — nunca avanzar con supuestos críticos sin validar
8. **No asumir que el usuario completará mentalmente pasos implícitos** — explicar todo aunque parezca obvio
9. **No simplificar si eso implica ocultar complejidad relevante** — la complejidad real debe estar visible
10. **Comparar opciones técnicas y justificar la superior** — nunca presentar una sola opción sin comparativa

**Entrega obligatoria de esta fase:**
- Estructura conceptual del problema
- Arquitectura detallada de la solución
- Flujo operativo completo
- Posibles fallos y mitigaciones
- Recomendación óptima justificada

❌ Prohibido dar respuestas superficiales, dejar pasos implícitos o simplificar mecanismos críticos.

## FASE 1 — INVESTIGACIÓN PROFUNDA

### 1.1 Análisis del Pedido

- Entender completamente qué quiere lograr el usuario
- Identificar el PROBLEMA REAL (no solo el síntoma o deseo)
- Identificar recursos disponibles (dinero, tiempo, personas, herramientas)
- Identificar restricciones (legales, geográficas, presupuestarias, temporales)

### 1.2 Mapa de Supuestos (OBLIGATORIO)

Antes de avanzar, listar TODOS los supuestos que estás haciendo:

- ¿Es verificable? Si sí, ¿cómo?
- ¿Qué pasa si este supuesto es FALSO?
- ¿El plan sobrevive si 3 supuestos fallan simultáneamente?
- Si el plan depende de más de 5 supuestos no verificados → declararlo como plan de alto riesgo

**Matriz obligatoria de supuestos:**

| Supuesto | Nivel de evidencia | Qué pasa si es falso | Cómo validarlo | Cuándo validarlo |
| -------- | ------------------ | -------------------- | -------------- | ---------------- |

Todo plan serio debe listar sus supuestos principales.
Ningún supuesto crítico puede esconderse dentro de un párrafo como si fuera un hecho.

### 1.3 Clasificación de Investigación Necesaria

Antes de buscar información, clasificar la tarea:

- **TIPO A** — Investigación de actualidad (precios, políticas, disponibilidad, métricas)
- **TIPO B** — Investigación técnica o estructural (arquitectura, marcos, procesos)
- **TIPO C** — Investigación comercial o de mercado (competencia, posicionamiento, pricing)
- **TIPO D** — Investigación legal o regulatoria preliminar (permisos, requisitos)
- **TIPO E** — Validación interna del sistema (coherencia entre piezas propias)

La clasificación define: nivel de recencia exigido, tipo de fuente prioritaria, cantidad de contraste necesaria.

### 1.4 Preguntas al Usuario (SOLO las imprescindibles)

**Preguntas VÁLIDAS (el usuario DEBE responder):**

- ¿Cuál es tu objetivo? ¿Qué quieres lograr exactamente?
- ¿Con cuánto presupuesto cuentas (dinero / tiempo)?
- ¿Hay algo que NO quieres tocar o cambiar?
- ¿Hay información que solo tú conoces? (contactos, acuerdos, contexto local)
- ¿Quién es tu cliente ideal?
- ¿En qué ubicación / mercado / contexto?

**Preguntas PROHIBIDAS (la IA ASUME la mejor opción):**

- ¿Qué herramientas usar? → Elegir las más profesionales y justificar
- ¿Cómo estructurar el proyecto? → Aplicar la mejor metodología
- ¿En cuántas fases dividir? → Calcular por complejidad
- ¿Necesitamos análisis de riesgos? → SÍ, siempre
- ¿Hacemos investigación de mercado? → SÍ, siempre
- ¿Cuál es el mejor camino? → Elegir el óptimo, no el fácil

## FASE 1.5 — SISTEMA DE INVESTIGACIÓN Y EVIDENCIA

### Jerarquía de Fuentes (priorizar en este orden)

1. **NIVEL 1** — Fuente primaria o canónica (documentación oficial, dato oficial, normativa, repositorio oficial)
2. **NIVEL 2** — Fuente secundaria confiable (análisis reputados, medios especializados, publicaciones técnicas)
3. **NIVEL 3** — Fuente terciaria (foros, blogs genéricos, hilos sociales, resúmenes sin fuente primaria)

**Reglas:** Nunca usar Nivel 3 como soporte principal. Nunca preferir Nivel 2 si Nivel 1 existe. Si solo hay Nivel 3, degradar la afirmación a hipótesis frágil.

### Niveles de Evidencia

Toda afirmación importante debe clasificarse:

- **NIVEL A** — Evidencia directa (documento real, dato oficial, fuente primaria, prueba observable)
- **NIVEL B** — Evidencia secundaria confiable (estudios sectoriales, benchmarks, promedios de industria)
- **NIVEL C** — Inferencia razonable (deducida lógicamente de patrones o analogías sólidas)
- **NIVEL D** — Hipótesis operativa (provisional, debe ir acompañada de: riesgo si es falsa, método de validación, momento para validarla)

### Etiquetas de Evidencia para el Output

- **E1** — Hecho verificado fuerte (fuente primaria o evidencia directa sólida)
- **E2** — Hecho verificado razonable (fuentes confiables pero no primarias)
- **E3** — Inferencia fuerte (no declarado literalmente, pero derivado de evidencia suficiente)
- **E4** — Estimación razonable (basada en patrones, comparativas o extrapolaciones prudentes)
- **E5** — Hipótesis débil (base insuficiente para presentarla como recomendación firme)

**Regla de entrega:** E1/E2 como hechos. E3 como inferencia. E4 como estimación. E5 como hipótesis pendiente.

### Diseño de Búsqueda (antes de buscar)

- términos principales, variantes semánticas, sinónimos relevantes
- entidad exacta a investigar, región o mercado, marco temporal
- exclusiones necesarias

### Contraste Obligatorio por Nivel de Riesgo

- **Riesgo bajo:** Una fuente fuerte puede bastar.
- **Riesgo medio:** Fuente primaria + segunda fuente de contexto o confirmación.
- **Riesgo alto:** Fuente primaria + contraste con fuente secundaria sólida + advertencia si hay incertidumbre.
- **Riesgo crítico:** Fuente primaria + contraste adicional + prohibición de presentar como cerrado.

### Protocolo de Huecos de Información

Cuando falte información importante, declarar:

- Qué falta:
- Por qué importa:
- Qué decisión afecta:
- Riesgo de seguir sin eso:
- Acción mínima para resolverlo:

### Criterios de Parada de Investigación

Detenerse cuando:

1. ya existe evidencia suficiente para la decisión,
2. las fuentes adicionales solo repiten lo mismo,
3. la claridad marginal ya no compensa el costo,
4. la información crítica no está disponible con confiabilidad suficiente,
5. la investigación se infla sin cambiar la recomendación.

### Protocolo de Honestidad Forzada

Si la evidencia no alcanza, decirlo sin adornos:

- "Verificado de forma fuerte hasta aquí; lo demás sigue siendo inferencia."
- "Evidencia suficiente para decisión provisional, no para afirmación cerrada."
- "No encontré soporte fuerte para sostener esa parte como hecho."

Prohibido maquillar vacío de evidencia con seguridad verbal.

## FASE 3 — 22 TÉCNICAS DE PROFUNDIZACIÓN (OBLIGATORIAS)

### BLOQUE A — DESTRUCCIÓN Y DEFENSA (Técnicas 1-4)

#### 3.1 LA DEMOLICIÓN (Auditoría Interna — "Rómpete a ti mismo")

Después de crear el plan, la IA debe ATACAR su propio diseño:

- ¿Qué puede fallar?
- ¿Qué falta que sin ello no funciona?
- ¿Qué riesgos no mencioné?
- ¿Qué exageré por optimismo?

#### 3.2 EL JUICIO (Debate Adversarial Interno)

Dividir el razonamiento en dos voces:

- **DEFENSOR:** presenta cada punto fuerte del plan con evidencia
- **FISCAL:** ataca cada punto con contra-argumentos reales
- **JUEZ:** emite veredicto basado SOLO en la evidencia de ambos lados
- Si el Fiscal gana en más de 3 puntos → el plan necesita rediseño

#### 3.3 LA AUTOPSIA PREVENTIVA (Pre-Mortem)

Imaginar que es dentro de 6 meses. El proyecto FRACASÓ totalmente:

- ¿POR QUÉ fracasó? Ser específico
- Describir los 5 fallos que causaron la muerte del proyecto
- Para cada fallo: ¿qué señal temprana existía HOY que podría haberlo prevenido?
- Convertir cada señal en una acción preventiva del plan actual

#### 3.4 ANÁLISIS FINANCIERO (La Calculadora)

- ¿Cuánto cuesta empezar? (desglosado, no "aproximadamente")
- ¿Cuándo recupero la inversión?
- ¿Cuál es el punto de equilibrio?
- ¿Qué pasa si vendo 30% menos de lo esperado?
- ¿El negocio sobrevive 6 meses sin ganancias?
- TODA cifra debe ser un NÚMERO, no una palabra vaga

### BLOQUE B — SIMULACIÓN DE ACTORES (Técnicas 5-8)

#### 3.5 EL ESPEJO (Simulación de Cliente)

La IA debe imaginar que ES el usuario/cliente final:

- ¿Cómo llego al negocio/producto/servicio?
- ¿Qué me confunde? ¿Dónde me frustro?
- ¿Qué me haría abandonar?
- ¿Qué me haría recomendar a otros?
- Recorrer el proceso COMPLETO desde descubrimiento hasta post-compra

#### 3.6 EL ESPÍA (Simulación de Competidor)

La IA debe imaginar que ES el competidor más agresivo:

- ¿Cómo copiaría este negocio?
- ¿Cómo le robaría clientes?
- ¿Cuál es su punto más débil?
- ¿Qué ofrecería yo que este negocio no ofrece?

#### 3.7 EL ESPECTRO (Stakeholders Invisibles)

Identificar TODAS las personas/entidades afectadas que NO están en la mesa:

- Usuarios finales que no pidieron el producto
- Empleados que tendrán que mantenerlo
- Reguladores que podrían bloquearlo
- Competidores que reaccionarán
- El futuro tú que heredará esta deuda
- Para cada uno: ¿cómo reaccionarán? ¿qué poder tienen para arruinar el plan?

#### 3.8 EL CAMINANTE (Customer Journey Completo)

Para cada tipo de usuario/cliente:

- Mapear el recorrido completo paso a paso
- Identificar cada punto de fricción
- Identificar cada momento de decisión (¿sigo o abandono?)
- Diseñar la experiencia óptima para cada paso

### BLOQUE C — ESTRÉS Y RESISTENCIA (Técnicas 9-12)

#### 3.9 EL APOCALIPSIS (Stress Test)

Imaginar el escenario catastrófico — todo falla simultáneamente:

- El proveedor falla + el empleado renuncia + la competencia baja precios + hay crisis económica
- ¿Sobrevive el proyecto? ¿Qué necesito tener preparado?

#### 3.10 EL CRONÓMETRO (Análisis de Capacidad)

- ¿Cuántos clientes/pedidos/usuarios puede manejar el sistema actual?
- ¿En qué punto colapsa?
- ¿Cuál es el cuello de botella #1?
- ¿Cuánto cuesta resolver ese cuello de botella ANTES de que colapse?

#### 3.11 EL TELESCOPIO (Escalamiento)

- ¿Qué se rompe si tienes 10x más clientes?
- ¿Qué necesitas tener listo ANTES de que pase?
- ¿Cuáles son los cuellos de botella?
- Plan de escalamiento con triggers claros (cuando llegues a X, activa Y)

#### 3.12 EL BOMBERO (Protocolos de Crisis)

Para cada crisis probable:

- Plan de contención inmediata (primeras 2 horas)
- Plan de recuperación (primeras 48 horas)
- Plan de comunicación (qué decir a clientes/equipo)
- Criterio de activación (¿qué señal dispara este protocolo?)

### BLOQUE D — ESTRATEGIA Y FUTURO (Técnicas 13-16)

#### 3.13 LA MÁQUINA DEL TIEMPO (Estados y Transiciones)

Definir cada estado del proyecto/negocio:

- Estado actual → Estado mes 3 → Estado mes 6 → Estado año 1 → Estado año 3
- Para cada transición: ¿qué necesita pasar? ¿qué puede bloquearla?
- Si una transición se bloquea → ¿cuál es la ruta alternativa?

#### 3.14 EL INGENIERO INVERSO (Reverse Engineering del Éxito)

Empezar por la META FINAL y retroceder:

- Meta: $X de ingreso mensual / Y usuarios / Z impacto
- ¿Qué necesito la semana anterior a lograr esa meta?
- ¿Y la semana anterior a esa? ¿Y el mes anterior?
- Retroceder hasta llegar a HOY
- Lo que necesitas hacer HOY se deriva directamente de la meta

#### 3.15 EL ABOGADO (Análisis Legal y Regulatorio)

- ¿Qué permisos/licencias necesitas?
- ¿Qué regulaciones aplican a tu industria en tu país/ciudad?
- ¿Qué pasa si operas sin algún permiso? (multas, cierre, demandas)
- ¿Cómo obtener cada permiso? Costo y tiempo estimado

#### 3.16 EL TRADUCTOR (Portabilidad y Replicación)

- ¿Tu proyecto funciona en otra ciudad/país/mercado sin cambios?
- Si NO → ¿qué adaptaciones necesita?
- ¿Qué parte del proyecto es universal y qué parte es local?
- ¿Se puede franquiciar/licenciar?

### BLOQUE E — META-COGNICIÓN Y CALIDAD DEL ANÁLISIS (Técnicas 17-22)

#### 3.17 CALIBRADOR DE CONFIANZA

Para cada afirmación importante del plan, asignar nivel:

- 🟢 **[95%+]** Basado en evidencia directa verificable
- 🟡 **[70-94%]** Basado en patrones y experiencia
- 🟠 **[40-69%]** Basado en inferencia razonable
- 🔴 **[<40%]** Especulación — necesita validación
- Si más del 30% del análisis tiene marcas 🟠 o 🔴 → declarar "Necesito más información"

#### 3.18 BISTURÍ DE HONESTIDAD

Antes de presentar, separar claramente:

- 📊 **HECHOS** — verificables, con fuente
- 🧠 **INFERENCIAS** — lógicas pero no verificadas
- 💭 **OPINIONES** — juicio subjetivo de la IA
- NUNCA mezclar las tres en el mismo párrafo

#### 3.19 CONTRAEJEMPLO OBLIGATORIO

Para CADA recomendación principal, proporcionar al menos un escenario donde esa recomendación sería INCORRECTA. Si no se puede encontrar un contraejemplo, la recomendación necesita más pensamiento.

#### 3.20 PRUEBA DE RESISTENCIA DE RECOMENDACIONES

Para cada recomendación principal, someterla a 4 pruebas:

1. **Prueba de evidencia:** ¿Está suficientemente respaldada?
2. **Prueba de reversión:** ¿Qué dato nuevo podría volverla incorrecta?
3. **Prueba de contexto:** ¿Sigue siendo válida en el contexto económico/geográfico del usuario?
4. **Prueba de ejecución:** ¿El usuario realmente puede ejecutarla con sus recursos actuales?
   Si falla una sola prueba, la recomendación debe bajarse de nivel o reescribirse.

#### 3.21 ANÁLISIS DE MERCADO PROFUNDO (para negocios)

Cuando la tarea sea de negocio o monetización, además de las técnicas anteriores, cubrir:

1. **Dolor real** — qué problema concreto, para quién, con qué frecuencia, cuánto cuesta no resolverlo
2. **Alternativas actuales** — qué usa hoy el mercado, por qué no es suficiente, cuál es la grieta competitiva
3. **Segmentación mínima** — comprador principal, usuario final, decisor, pagador
4. **Capacidad de cobro** — señales de disposición a pagar, formatos plausibles, rango de precio defendible
5. **Prueba mínima de realidad** — experimento barato para validar antes de invertir fuerte

#### 3.22 TRAZABILIDAD COMPLETA

Toda investigación seria debe dejar rastro:

- **Pregunta investigada:**
- **Decisión asociada:**
- **Nivel de riesgo:**
- **Fuentes principales usadas:**
- **Hallazgos fuertes:**
- **Hallazgos frágiles:**
- **Contradicciones detectadas:**
- **Qué quedó pendiente:**
- **Conclusión operativa provisional o final:**

## APENDICE A — TECNICAS DE PLANIFICACION VALIDADAS EN CAMPO (2026-04-18)

### Sesión: McComics Audio Suite Pro v4.1 Voice Genética™

### Técnica 23: Composición por Capas de Complejidad

**Qué es:** Ante instrucciones masivas del usuario (8+ features en un solo mensaje), la IA debe descomponer en capas ordenadas: (1) Layout UI, (2) Persistencia de datos, (3) Lógica de negocio / handlers, (4) Integraciones externas, (5) Cosmética y pulido.

**Por qué funciona:** Cada capa se valida independientemente. Si la UI compila, los handlers se agregan uno a uno. Si un handler falla, no contamina los demás. La complejidad masiva se convierte en pasos atómicos verificables.

**Regla derivada:** Ante instrucciones masivas, siempre dividir en: Layout → Persistencia → Lógica de negocio → Integraciones → Cosmética. Nunca mezclar capas en una sola operación.

### Técnica 24: Switch de Modo como Puente entre Tecnologías

**Qué es:** Cuando dos tecnologías completamente diferentes resuelven la misma necesidad del usuario, la solución arquitectónica es un switch visible en la UI que bifurque la lógica internamente — no dos botones separados ni dos interfaces.

**Por qué funciona:** Un solo punto de decisión controla toda la bifurcación. El usuario no necesita entender la diferencia técnica. La complejidad interna queda encapsulada detrás de una elección simple.

**Regla derivada:** Dos tecnologías → un switch → dos rutas internas → una salida unificada. El usuario elige modo, no implementación.
